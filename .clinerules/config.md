# snapshot-processor Configuration & Secrets Management

snapshot-processor keeps **configuration and secrets out of the image** and
resolves them at container start from 1Password Secrets Automation, through
a `.env` file, into interpolated config files. This file documents that flow
and the conventions a fork must preserve when it adapts the secret store.

## 1. The flow

```
1Password vault (ENV.<project>)  →  .env  →  container env  →  config_interpol  →  runtime config
```

1. **`.env` generation** (`make configure`): `base.env` (static defaults) is
   copied, then `dot_env_setup.sh` runs inside the container and appends
   secrets pulled from 1Password via `cred_tool`. The result is sanity-checked
   with a minimum line count.
2. **Container env**: `docker-compose.yml` reads `env_file: .env` and mounts
   the 1Password service-account/connect tokens as Docker secrets.
3. **Config interpolation**: the inherited `base_entrypoint.sh` runs
   `uv run --frozen --no-sync config_interpol < config/app.conf > app.conf`,
   substituting `%(VAR)s` placeholders with environment values.
4. **Runtime config**: the interpolated file lands at `/opt/app/app.conf`.
   AWS configuration and credentials are generated by `aws_configure` (run
   from `backup_auth_token.sh`, driven by `app_entrypoint.sh` and the
   `backup_auth_token` cron job).

## 2. 1Password Secrets Automation

- The source of truth is a 1Password vault entry named `ENV.<project>`
  (e.g. `ENV.snapshot-processor`). `dot_env_setup.sh` calls
  `uv run --frozen --no-sync cred_tool "ENV.${PROJECT_NAME}" "${PROJECT_NAME}" build`.
- The Connect server is expected to already be running; the container reaches
  it via `OP_CONNECT_HOST` (default `http://host.docker.internal:8080`) and
  the `op_service_account_token`/`op_connect_token`/`op_vault` Docker secrets.
- The Python app validates credentials at startup via
  `Creds().validate_creds()` (pylib) before initializing Sentry.

**Rule:** never hardcode or commit secrets. `.env` values are development
defaults only; the real values live in 1Password. If a fork replaces
1Password (e.g. with Bitwarden), it must preserve the same boundary — a
`dot_env_setup.sh` that emits `KEY=value` lines and a `cred_tool`-equivalent
entry point — so the rest of the flow is unchanged.

## 3. Config interpolation

- `config/app.conf` is a **template** using `%(VAR)s` placeholders (Python
  `configparser`-style, not `$VAR`).
- `config_interpol` (a pylib entry-point script) substitutes them from the
  environment at container start.
- The active `[program:*]` blocks are generated by the inherited
  `base_entrypoint.sh` and by `app_entrypoint.sh` (see `container.md`).

**Rule:** put per-environment values behind a `%(VAR)s` placeholder and let
`config_interpol` resolve them; do not bake environment-specific values into
the config templates.

## 4. Feature switches

Every integration is gated by an environment variable or an `app.conf`
section so the app runs with zero external dependencies:

- Runtime programs: `NO_PYTHON_APP`, `NO_CRON` (see `container.md`), and
  `RUN_FTP_SERVER` (the FTP server program appended by
  `app_entrypoint.sh`).
- FTP passive mode: `FTP_PASV_MIN_PORT`/`FTP_PASV_MAX_PORT` (default
  `30000-30009`, must also be published in `docker-compose.yml`) and
  `FTP_MASQUERADE_ADDRESS` (the address advertised to clients; required when
  the container sits behind Docker's NAT, otherwise clients are handed the
  container's private address and transfers stall after login).
  **Set `FTP_MASQUERADE_ADDRESS` to the address clients actually connect to**
  (e.g. the docker host's LAN IP). It is not optional for PASV-only firmware:
  without it the `227` reply advertises the bridge address (`172.x.y.z`) and the
  camera fails with `No route to host` — it logs in, `DELE`/`CWD` succeed and no
  `STOR` ever arrives. Clients that negotiate `EPSV` (or that ignore the PASV
  address, as curl and ftplib do by default) are unaffected, so a successful
  upload from a workstation does not prove the cameras can upload. Like every
  other runtime value it must live in the 1Password `ENV.<PROJECT_NAME>` item,
  because `make configure` regenerates `.env` from it.
- FTP logging: `FTP_LOG_LEVEL` (default `WARNING`) controls the pyftpdlib
  logger; per-command lines (session open, `USER`, `CWD`, `DELE`, `PASV`,
  `STOR`) are only emitted at `INFO`/`DEBUG`, and are the fastest way to see
  what a camera is doing. The `[program:ftp]` block in `app_entrypoint.sh` does
  not route to `/dev/stdout`, so supervisord writes those lines to
  `/data/ftp-{stdout,stderr}---supervisor-*.log`.
- Snapshot timestamps: `CAMERA_TIMEZONE` (falls back to `TZ`, then the
  container's local zone) is the zone used to interpret camera file names such
  as `HMDAlarm_20261102-105249.jpg`/`MDAlarm_20261101_063000.jpg`, which carry
  local time without an offset. Files this application writes itself use a
  `<operation>_<device>_<unix epoch>.jpg` name and are unaffected.
- Uploaded artefacts and archiving: any file a camera drops under
  `uploads/snapshots/<location>/` (any depth below it, any file name) is
  associated with that device; a file outside a configured camera path is logged
  as unmapped and ignored. Still images (`.jpg`, `.jpeg`, `.png`) follow exactly
  the same rules whether they were pulled from a camera or uploaded by one: they
  are analysed, and the image itself is **not** archived — only its derived
  artefacts are (`detect_*` annotated result, `human_*` marker). Anything that
  cannot be analysed, notably the cameras' `.mkv` alarm clips under
  `<camera>/record/`, skips detection and goes straight to cloud storage. This
  lives in `GoogleDriveUploader._should_archive()`. The uploader only runs image
  validation (`Image.open(...).verify()`) on `image/*` MIME types, waits for an
  upload to stop growing before using it (`wait_for_settled_snapshot()`), and
  never overwrites an upload: `create_derived_snapshot_path()` prefixes
  (`detect_<camera name>.jpg`) and `mark_human_snapshot()` copies the original to
  `human_<camera name>.jpg`.
- Recording gate: a recording (any `video/*` upload, i.e. the `.mkv` clips) is
  archived **only** when the same device detected a person/face within
  `RECORDING_DETECTION_WINDOW_SECONDS` (default `60`) of the recording's
  timestamp, on either side. Hits are tracked in `DetectionRegistry` from the
  detector's own timestamps, so a pulled still can justify a clip and vice versa.
  A clip with no matching hit is held for `window + 30 s` (a detection may still
  be in flight) and then discarded; `GoogleDriveUploader._hold_recording()` and
  `_resolve_pending_recordings()` implement the decision.
- Local retention (`config/cron/cleanup_snapshots`, installed into the app user's
  crontab at build time — a rebuild is needed to change it): the archive payload
  (`detect_*`/`human_*`) and anything unexpected survive 48 h (`-mmin +2880`,
  swept hourly at :30); recordings (`*/record/*`, `*.mkv`, `*.mp4`) are pruned
  after 6 h; `fetch_*` snapshots after 2 h — they are analysis input and are
  never archived. A recording that is discarded by the gate is deleted
  immediately. Keep clips' retention above any plausible archive retry window.
- Object detection: `OBJECT_DETECTION_ENABLED` and the pylib managed feature
  flags `object-detection`, `cloud-object-detection`, `local-object-detection`,
  `cloud-storage-management` (resolved via 1Password `flags/...` entries).
- Optional integrations: `HC_PING_URL` (Healthchecks), `CRONITOR_MONITOR_KEY`
  (Cronitor), `AWS_DEFAULT_REGION` (AWS CLI),
  `SYSLOG_ADDRESS` (syslog routing via pylib).

**Rule:** a new integration gets a feature switch, never a hard dependency.

## 5. Key environment contract

The minimum env contract a fork inherits (see `base.env` and the 1Password
vault):

- `PROJECT_NAME` — vault entry and container naming.
- `CONTAINER_NAME` — the Docker image tag.
- `APP_NAME` — application name for logging and `service.name` default.
- `DEVICE_NAME` — container hostname.
- `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES` — optional observability
  identity. If set, the pylib-provided OTEL SDK reads them via its standard
  environment detectors (see `observability.md`).

Secrets (never in `base.env`): `OP_CONNECT_HOST`, `OP_CONNECT_TOKEN`,
`OP_CONNECT_VAULT`, `HC_PING_URL`, `CRONITOR_MONITOR_KEY`, and the Sentry DSN
(`Sentry/__APP_NAME__/dsn`). Project-specific runtime values (RabbitMQ
server/exchange/topic, FTP user/password, Google Drive folder, AWS S3
backup bucket, camera/input/output mappings) are also resolved from the
1Password vault.
